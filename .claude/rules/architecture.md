# アーキテクチャ／技術スタック方針

## ライブラリ・フレームワーク選定

- メンテナンスコストとセキュリティの観点から、**安全で実績のあるライブラリ・フレームワーク・OSS・SaaSを優先**する。
- **車輪の再発明を避け、オリジナルコードを少なく保つ。** 認証・決済・画像処理・通知など、信頼できるライブラリ／SaaSがある領域は自前実装しない。
- 採用前に `.claude/OWASP10.md`（A06 脆弱または古いライブラリの使用）の観点でメンテナンス状況・脆弱性情報を確認する。

## 基本スタック（`requirements.md` が現行MVPの正）

| 用途 | 技術 |
|---|---|
| フロントエンド | Next.js（TypeScript） |
| バックエンドAPI | Ruby on Rails（APIモード） |
| DB | PostgreSQL（開発はSQLite） |

## 必要に応じた拡張

- **AI／解析・画像加工**：Python + FastAPI（+ LangChain等）
- **高速並列処理・リアルタイム通信**：Gin（Go）
  - 現行のMVPエディションでは `requirements.md` の判断により**Ginは採用しない**（30秒ポーリングで需要検証には十分なため）。これは今後、リアルタイム要件が明確になった場合に選択肢として残す一般方針であり、現行MVPの決定を上書きするものではない。

## 規模に応じた構成の意識

サービス規模が拡大する場合、次を意識して設計する（現行MVPでの導入を強制するものではない）。

- **マイクロサービスアーキテクチャ**：機能単位でのサービス分割
- **MVCアーキテクチャ**：責務分離（Rails APIは既にMVC準拠）
- **API Gateway**：複数バックエンド（Rails/FastAPI/Gin）が並存する場合のエントリポイント統一
- **メッセージング**：非同期処理・サービス間連携が必要になった場合のキュー導入（現行MVPは同期処理・ピギーバック方式で十分なため未導入）
