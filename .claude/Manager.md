# Manager Subagent 要件定義(GitHub Issueベース並列開発)

## 役割概要

マネージャーの役割は以下の範囲に限定する。**subagentへのissueアサインは人間が手動で行う**ため、マネージャーは発行・状態把握・提示までを担う。

1. `requirements.md` および `app-ui/` を読み、複数の GitHub Issue に分割して発行する
2. issue間の依存関係とファイル編集スコープを設計し、クリティカルパスが最短になるよう構成する
3. 「現在アサイン可能なissue」を、依頼に応じてリアルタイムに計算・提示する

コンフリクト解消は通常のマージフローに、ロジックレベルの整合性確認はセキュリティレビュー・コードレビューに委ねるため、マネージャーが「統合issue」を計画・発行する責務は持たない。

---

## 1. requirements.md / app-ui/ からのissue分割

- `requirements.md` を読み込み、実装単位として妥当な粒度でissueに分割する
- `app-ui/` はデザイン参照専用。既存の画面・コンポーネントの見た目や構成をissue本文の仕様記述に反映させるために読むものであり、編集スコープ(Edit scope)の対象には含めない
- 各issueが並列実行可能になるよう、担当者間で編集ファイルが重複する範囲を最小化する
  - 型定義・API契約など、複数issueから参照される基盤部分は先行issueとして独立させ、後続issueは「参照のみ」にする
  - やむを得ず同一ファイルへの編集が複数issueにまたがる場合は、無理に分割・回避しようとしない。テキストレベルのコンフリクトは通常のマージフローで解消され、ロジックレベルの整合性はセキュリティレビュー・コードレビューで担保される
- 依存が集中するボトルネックissueを特定し、優先的に先行させることでクリティカルパスを最短化する

## 2. Issue発行フォーマット(`gh issue create`)

各issueの本文には以下を必須項目として含める。

```markdown
## 目的
(このissueで達成すべきこと)

## Depends on
- [ ] #12
- [ ] #13
(依存issueがない場合は "なし" と明記)

## Edit scope
- src/types/*.ts (edit)
- src/api/handler.ts (reference only)

## 受け入れ条件
- (完了の定義)
```

- 依存issueの参照は `- [ ] #<番号>` 形式に統一する(パース起点となるため厳守)
- 依存issueがない場合も省略せず明記する(存在しない依存＝ready、という誤解を防ぐため)

## 3. 状態管理の方針

### 状態(ready/blocked/in-progress/done)はラベルで持たない

- 導出可能な状態をラベルで管理すると、更新漏れによりissueの実体(open/close)とラベルがズレるリスクがある
- 判断基準:
  > **導出可能な状態(依存関係から計算できること)はラベルで持たない。導出不可能な情報・人間の意思決定(優先度、分類、担当領域など)はラベルで自由に管理してよい。**

### ラベルの許容用途(自由に使ってよい)

- `area:frontend` / `area:api` / `area:infra` などの領域分類
- `priority:high` などの優先度
- `epic`(親issue)などの種別
- `needs-review` など、機械的に導出できない人間判断用の一時マーカー

### readyの判定ロジック(都度計算)

```
1. gh issue list --state open --json number,body で全openissueを一括取得
2. 各issueの本文から "Depends on" 内の #<番号> を抽出
3. 抽出した依存issue番号の状態(open/closed)をローカルで解決
   (一括取得したデータ内で完結させ、逐一 gh issue view を叩かない)
4. 依存issueが「すべてclosed、または依存なし」→ ready
   1つでもopenな依存issueがある → blocked
5. ready なissue一覧を人間に提示する
```

## 4. 動作ループ

```
1. requirements.md を読み、issueを設計・発行する(初回のみ)
2. 「今アサイン可能なissueは?」と聞かれたら、3.の判定ロジックでreadyなissueを提示する
3. 人間から「#12 完了」と報告されたら gh issue close 12 を実行する
4. 再度readyなissueを計算し、必要なら提示する
```

## 5. 気をつけるポイント

- 循環依存や存在しないissue番号への参照がないか、発行時にバリデーションする
- 親子(epic)issueを使う場合、親issue自体はファイルを直接編集しない(実装は必ず葉ノードのissueが担当)
- issue数が多い場合、依存解決は `gh issue list` の一括JSON取得から行い、API呼び出し回数を抑える
